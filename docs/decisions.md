# Decisions

Recorded on 2026-09-27. Where this file differs from the plan in the [feasibility report](feasibility-report.md), this file wins.

1. **One native binary.** iunctus is a single Rust binary. It does not bundle or call the nextflow, snakemake, cwltool or argo binaries, and it needs no JVM and no Python install. The tools inside tasks still run in containers, on a local container runtime or through TES.
2. **Languages in scope:** Nextflow, Snakemake, CWL, Argo Workflows and plain script workflows. The goal is to run a large, commonly used subset of each language, not every feature.
3. **Nextflow first.** It is the largest problem.
4. **Real workflows decide the scope.** For Nextflow, the first target is nf-core: its pipelines, modules and subworkflows. Features are added in the order that unlocks the most pipelines. After that come the Nextflow, CWL and Snakemake workflows on WorkflowHub. Galaxy workflows (49% of WorkflowHub on 2026-09-27) are out of scope for now.
5. **Nextflow strict syntax only.** This is the syntax of the v2 parser, the default since Nextflow 26.04. There is no full Groovy support. Unsupported features fail at load time with a clear error.
6. **Core rules first, library later.** The core must be right from the start: the evaluation rules of the Groovy subset, channel semantics, config semantics and the typed syntax. The library grows with the test workflows: GDK methods, operators, stand-ins for Java classes, directives and plugin functions.
7. **No Nextflow work directory.** Tasks run in scratch directories. Inputs and outputs live in content-addressed storage. A shared cache is keyed on the concrete task and has rules for deterministic and non-deterministic steps.
8. **TES first; Aruna later.** The first executor is GA4GH TES. Aruna is not a special target for now; it will follow the TES support instead. (Decided 2026-09-27; this replaces "Aruna first" in item 7.)
9. **Storage: native S3 and file system.** Both hold the cache directory: `cas/<digest>` for file contents and `ac/<cache key>` for one manifest per finished task. The manifests next to the files are the source of truth, so a cache on S3 can be shared across machines.
10. **An embedded database instead of a work directory.** A database file next to the cache holds the task graph, the event log for resume, attempts and log pointers, and a local copy of the cache index.
11. **Container-only execution is a hard constraint.** Every workflow task runs in a container, including local tasks, retries, stubs and workflow test tasks. A missing image or unavailable container executor is an error before execution; there is no host execution fallback. External commands requested by workflow code follow the same rule. Planning and expression evaluation remain inside the native interpreter.
12. **Conda prepares containers.** A Conda environment definition is resolved to locked packages for the target platform, then built into a container image. Package installation and installation scripts run inside the container build environment; no host Conda installation is required. Prepared images are reused by locked environment, base image digest, target platform and build recipe. The final image digest identifies the software environment in the task cache key; the environment YAML alone is insufficient.
13. **Images per environment, with a workflow-wide option.** The default is one image per distinct environment. A user may also supply one image containing all tools required by a workflow, or prepare a workflow-wide image from its Conda definitions. Separate environments inside that image preserve conflicting tool versions; each task's environment selection is part of its hashed arguments or environment. Both options keep all task execution inside containers.
14. **Every nf-core pipeline must load and run.** (Decided 2026-09-28; this widens item 5.) Where a pipeline relies on syntax that Nextflow's strict parser rejects but the legacy parser accepts, like `try`/`catch` around `includeConfig`, `if` statements and variable declarations in config files, or statements between script declarations, iunctus accepts it with the legacy meaning. Strict syntax stays the reference for everything both parsers accept. The same holds for Groovy classes in `lib/` and for Java libraries that earlier Nextflow releases shipped and old pipelines call, like the everit JSON Schema validator and `org.json`: iunctus provides native stand-ins, even where Nextflow 26.04 no longer runs those pipelines. This also covers DSL1 scripts, which Nextflow ran until 22.10 and which archived nf-core pipelines still are (widened 2026-09-29): each process reads `from` channels and writes `into` channels where the script defines it, and iunctus lowers such a script onto the dataflow model of DSL2, with an entry workflow that runs the statements and calls each process in place.
15. **One execution graph for all languages.** Every driver implements the `Driver` interface of the `workflow-graph` crate and asks for language-neutral tasks. The engine records every task and the files and orderings between them as the execution graph of the run, which `iunctus graph` prints. The graph grows during the run, because Nextflow channels, Snakemake checkpoints, CWL scatter and Argo `withParam` only know their tasks at run time.
16. **A mock TES executor until the real one.** The mock writes the TES v1.1 task document of each task and makes empty output files, so every workflow runs through without containers or a server. It is the default executor of `iunctus run` until the TES executor exists.
17. **Embedded code runs in native interpreters.** Snakemake's Python and CWL's JavaScript are evaluated inside iunctus, like Nextflow's Groovy, with native stand-ins for the library calls that real workflows make (for example `pandas.read_csv`). No Python or Node.js install is needed.
18. **Argo without Kubernetes, for the common scientific subset.** (Decided 2026-09-29.) iunctus runs Argo Workflows without a Kubernetes cluster and does not aim for full compliance. It supports what scientific workflows commonly use: container and script templates, steps, DAGs, loops, conditions, retries, parameters, artifacts, HTTP templates and executor plugins. ConfigMaps and volumes are supported where they map onto task inputs, outputs and files. A `hostPath` volume is a path on the machine that runs iunctus: a task reads its files, and unless the mount is read-only, the files that the task writes there are written back to that path. Mock runs never write to host paths. Init containers run as their own tasks, before the task they belong to and on the same files. A `resource` template that creates an Argo Workflow, or submits a WorkflowTemplate, runs that workflow as part of the same run: its tasks join the execution graph, so a workflow can start other workflows. Other features that only work inside a cluster, like `resource` templates that create Deployments, Services or Jobs, `data` templates, sidecars and daemon containers, are not supported: a workflow that uses them fails at load time with a clear error (exit code 33). Kubernetes fields that do not change what a task computes, like `podSpecPatch`, node selectors or tolerations, are ignored with a warning. A task's `command` and `args` form one command line; the executor runs it as given.

## Open questions

- Which embedded database: SQLite (mature, safe for several processes sharing one file) or Turso (pure Rust, concurrent writes; multi-process access still experimental in 2026-09). Recommendation: SQLite behind a small internal interface with portable SQL, and a switch to Turso once its multi-process access is stable.
