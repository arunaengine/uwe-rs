# Nextflow: language, runtime, and what a native Rust implementation needs

Research date: 2026-09-27. Primary sources: a shallow clone of `nextflow-io/nextflow` at commit `bbf6ff0` (25 Sep 2026, version file `26.09.1-edge`), shallow clones of `nextflow-io/language-server`, `nextflow-io/tree-sitter-nextflow`, `nextflow-io/nf-ga4gh` and `nf-core/rnaseq` (all taken 2026-09-27), the GitHub API, and the nf-core website. GitHub `master`/`main` links below point to files that were checked in these clones. The rendered Nextflow docs now live at `docs.seqera.io/nextflow/...` (`nextflow.io/docs/latest/reference/syntax.html` redirects there with HTTP 302). The docs sources are the `.mdx` files in the Nextflow repo, which are cited directly.

## Q1. Current version, release cadence, and how the language is changing (DSL2, strict syntax, types, records, params, outputs, topics)

### Takeaway
The latest stable release is 26.04.6 (9 Jul 2026). The latest edge release is 26.09.1-edge (25 Sep 2026). The next stable release (26.10) is due in October 2026. The strict syntax parser (v2) has been the default since 26.04 (April 2026). Nextflow is moving fast toward a statically typed language with records, typed processes and workflows, a `params` block and an `output` block. All new features require the strict parser.

- GitHub releases (checked 2026-09-27): `v26.09.1-edge` (2026-09-25), `v26.09.0-edge` (2026-09-22), `v26.08.0-edge` (2026-08-20), `v26.07.0-edge` (2026-07-15). - Conflict: the `CHANGELOG.md` on `master` lists 26.04.3 (28 May 2026) as its newest stable entry. It does not list 26.04.4 to 26.04.6, which exist as GitHub releases. Source: [CHANGELOG.md](https://github.com/nextflow-io/nextflow/blob/master/CHANGELOG.md); [releases](https://github.com/nextflow-io/nextflow/releases)
- 26.04 was released on April 29, 2026 (changelog says 28 Apr). Source: [docs/migrations/26-04.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/26-04.mdx)

Source: [docs/migrations/26-04.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/26-04.mdx)

- Recent edge changes (not yet in a stable release): "Direct execution of named workflows (#7379)", "Deprecate storeDir and document alternative approach (#7574)" and "Remove support for nf-weblog (#7639)" in 26.09.0-edge. "Type checking (#7656)" in 26.09.1-edge. Source: [CHANGELOG.md](https://github.com/nextflow-io/nextflow/blob/master/CHANGELOG.md)

- The grammar and syntax reference now include an `agent` definition with `input:`, `output:` and `prompt:` sections (an LLM-agent primitive). An ADR for it is dated 2026-08-01. The repo contains `plugins/nf-agent` and `plugins/nf-agent-pi`. Source: [docs/reference/syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/syntax.mdx); [adr/20260801-agent-primitive.md](https://github.com/nextflow-io/nextflow/blob/master/adr/20260801-agent-primitive.md)
- Typed and legacy scripts can call each other. "A given script must be entirely typed or entirely legacy (controlled by the `nextflow.enable.types` flag)." The runtime converts channel types at call sites. Source: [adr/20260310-typed-workflows.md](https://github.com/nextflow-io/nextflow/blob/master/adr/20260310-typed-workflows.md)

### Inferences
- A native implementation faces a moving target. Nextflow ships a new edge release every month. It adds language features in almost every stable release (params block and outputs in 25.10, records, typed workflows and modules in 26.04, agents and type checking in 26.09 edge).
- Two language "generations" coexist today: legacy DSL2 (untyped tuples, `publishDir`) and typed DSL2 (records, typed processes, `output` block). Real pipelines are almost all in the first generation today (see Q8). A native interpreter must start with untyped strict-syntax DSL2. It should plan for records and typed processes, because nf-core plans to require them by Q2 2027.
- Targeting "strict syntax only" is now a defensible choice. It is the default parser since 26.04, and the legacy parser is announced for removal.

### Gaps
- No public date was found for removing the legacy (v1) parser entirely.
- No release notes for 26.10 exist yet. It was not verified which edge features will ship as stable in 26.10.

## Q2. How formally the language is defined, and where the grammar lives

### Takeaway
Nextflow now has a real formal grammar. It is written in ANTLR 4 in `modules/nf-lang` and derived from the Groovy 4 grammar. There are separate script and config grammars, plus a syntax reference and a new semantics reference in the docs. The parser still produces a Groovy AST, and scripts still run as Groovy. So the grammar is formal, but the runtime semantics are still defined by Groovy plus the Nextflow runtime.

### Cited Findings
- Grammar files at commit `bbf6ff0` (25 Sep 2026), in `modules/nf-lang/src/main/antlr/`: `ScriptParser.g4` (872 lines, 109 parser rules), `ScriptLexer.g4` (873 lines, about 191 lexer rules and fragments), `ConfigParser.g4` (580 lines, 69 parser rules), `ConfigLexer.g4` (840 lines). Total 3,165 lines. Counted locally from the clone. Source: [modules/nf-lang/src/main/antlr](https://github.com/nextflow-io/nextflow/tree/master/modules/nf-lang/src/main/antlr)
- The header of `ScriptParser.g4` says: "Grammar specification for the Nextflow scripting language. Based on the official grammar for Groovy: https://github.com/apache/groovy/blob/GROOVY_4_0_X/src/antlr/GroovyParser.g4". Source: [ScriptParser.g4](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-lang/src/main/antlr/ScriptParser.g4)
- Top-level script rules in the grammar include: `featureFlagDeclaration`, `includeDeclaration`, `importDeclaration`, `paramsDef` (plus `paramDeclarationV1` for legacy `params.x = ...`), `recordDef`, `enumDef`, `processDef` (directives, inputs, `stage`, outputs, `topic`, `when`, `exec`, `stub`), `agentDef`, `workflowDef` (takes, emits, publishers), `outputDef` and `functionDef`. Source: [ScriptParser.g4](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-lang/src/main/antlr/ScriptParser.g4)
- The only statement forms are: if/else, try/catch, `return`, `throw`, `assert`, variable declaration, multiple assignment (`def (a, b) = ...`), assignment, expression statement, and empty statement. There are no loop or switch statements. Expressions keep most Groovy operators: power, arithmetic, shifts, ranges (`..`, `..<`), `as` casts, `instanceof`, `in`, `<=>`, regex find/match (`=~`, `==~`), bitwise and logical operators, ternary and Elvis (`?:`), safe navigation (`?.`) and spread-dot (`*.`). Source: [ScriptParser.g4](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-lang/src/main/antlr/ScriptParser.g4)
- `ConfigParser.g4` has config-specific top-level rules: `configInclude`, `configAssign`, `configBlock`, `configSelector` (for `withName:`/`withLabel:`), `configApplyBlock`. It shares the expression and statement grammar with the script parser. Source: [ConfigParser.g4](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-lang/src/main/antlr/ConfigParser.g4)
- `nf-lang` is 160 Java files and about 24,900 lines, with no Groovy sources. It contains `ast`, `control`, `dsl`, `formatter`, `namespaces`, `parser` and `types` packages. The `types/shim` package declares the typed standard library surface: `String`, `List`, `Map`, `Set`, `Iterable`, `Path`, `Duration`, `MemoryUnit`, `Integer`, `Float`, `Bag`. Counted locally. Source: [modules/nf-lang](https://github.com/nextflow-io/nextflow/tree/master/modules/nf-lang)
- The strict-parser ADR (accepted 2025-05-08) states the old problem: "No formal grammar. Because scripts are parsed as arbitrary Groovy, there is no canonical definition of the Nextflow language." It lists as a non-goal: "Replacing the Groovy runtime. Nextflow code should still compile and run as Groovy scripts." The decision: "The parser should check for syntax and semantic errors and produce the same Groovy AST as the legacy parser." The parser lives in `nf-lang` and is shared by the runtime, linter, formatter and language server. Source: [adr/20250508-strict-syntax-parser.md](https://github.com/nextflow-io/nextflow/blob/master/adr/20250508-strict-syntax-parser.md)
- The docs contain a syntax reference ("the Nextflow language specification") and a newer `reference/semantics.mdx`. The semantics page covers values (truthiness table, numbers, strings, collections, maps, records, tuples, closures), operators, statements, functions, processes, workflows, scripts, and types (nullable types, generics, records, enums, casting). Source: [docs/reference/syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/syntax.mdx); [docs/reference/semantics.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/semantics.mdx); rendered at [docs.seqera.io/nextflow/reference/syntax](https://docs.seqera.io/nextflow/reference/syntax)
- The Nextflow language server (Groovy/Java, Gradle build) depends on `io.nextflow:nf-lang:26.09.0-edge` and Groovy 4.0.31. Its latest release is `v26.04.4` (2026-09-16). Source: [language-server build.gradle](https://github.com/nextflow-io/language-server/blob/main/build.gradle); [language-server releases](https://github.com/nextflow-io/language-server/releases)
- `tree-sitter-nextflow` v0.4.0 (2026-09-23) was "rewritten from scratch to mirror the official Nextflow grammar (`ScriptParser.g4`)". It covers strict-syntax declarations (params blocks, records, enums, the output block, agents, typed functions, typed process and workflow sections). The first public release claimed "a 100% error-free parse rate over the pinned nf-core/modules corpus (2077/2077 files)". A CI job re-parses every `.nf` file of a pinned nf-core/modules commit and fails on any error. It has Rust, Python, C and Node bindings. `grammar.js` is 866 lines. The repo has one grammar (`grammar.js`) that mirrors `ScriptParser.g4`. No separate config grammar was found in it. Source: [tree-sitter-nextflow CHANGELOG](https://github.com/nextflow-io/tree-sitter-nextflow/blob/main/CHANGELOG.md); [parse-rate workflow](https://github.com/nextflow-io/tree-sitter-nextflow/blob/main/.github/workflows/parse-rate.yml)
- The `tree-sitter-nextflow` crate is not on crates.io. The crates.io API answered "crate `tree-sitter-nextflow` does not exist" on 2026-09-27. The README says to add the Rust binding as a path or git dependency. Source: [crates.io API](https://crates.io/api/v1/crates/tree-sitter-nextflow); [tree-sitter-nextflow README](https://github.com/nextflow-io/tree-sitter-nextflow)
- Older or community grammars exist: `matthuska/tree-sitter-nextflow`, `matthuska/tree-sitter-nextflow-config` (a config grammar), and `Sam-Sims/tree-sitter-nextflow`. Source: [matthuska/tree-sitter-nextflow](https://github.com/matthuska/tree-sitter-nextflow); [Sam-Sims/tree-sitter-nextflow](https://github.com/Sam-Sims/tree-sitter-nextflow); GitHub search results

### Inferences
- A Rust implementation can reuse the official grammar as its specification. About 180 parser rules across script and config is a manageable size. Options: (a) use `tree-sitter-nextflow` v0.4.0 through its Rust binding (git dependency) and build a typed AST on top of it; (b) port the ANTLR rules to a hand-written recursive-descent parser. Option (a) is fastest for scripts. A config grammar must still be written, and the ANTLR `ConfigParser.g4` is the reference for it. Newline-sensitive statement termination (handled by a custom scanner in tree-sitter-nextflow) is the trickiest lexing detail.
- The grammar still parses `import` (rule `importDeclaration`) although the docs list `import` as removed. This is likely kept to give a clear error message. This is an inference; it was not verified in `ScriptAstBuilder`.
- "Formally defined" applies to syntax only. Evaluation semantics come from Groovy's dynamic runtime (method dispatch, GDK methods, number promotion). A native implementation must re-specify these from the semantics doc and from observed behavior.

### Gaps
- There is no machine-readable semantic specification or conformance test suite for the language. The `tests/` and `validation/` directories in the repo are integration tests, not a conformance suite. Their use as a test oracle was not checked in depth.
- It was not verified whether `tree-sitter-nextflow` is used in production by Seqera, or only for editors (Zed) and ast-grep.

## Q3. Runtime semantics

### Takeaway
Nextflow runs a dataflow network built on GPars. Channels are either queue channels or value channels. Each process fires one task for each complete set of inputs. Each task runs in its own hashed work directory through a generated Bash wrapper (`.command.run`) around the user script (`.command.sh`). Task hashes (MurmurHash3 128-bit over many inputs) drive `-resume` through a LevelDB cache. Much of this behavior is implicit and is documented only in prose, code and changelogs.

### Cited Findings
- Dependencies of the core runtime: Groovy 4.0.33 (plus groovy-nio, -xml, -json, -templates, -yaml), GPars 1.2.1 and LevelDB (`org.iq80.leveldb:leveldb:0.12`). Source: [modules/nextflow/build.gradle](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/build.gradle); [root build.gradle](https://github.com/nextflow-io/nextflow/blob/master/build.gradle)
- The core runtime module `modules/nextflow` has 567 Groovy source files and about 97,000 lines of Groovy and Java. 87 files import `groovyx.gpars`. Counted locally from the clone. Source: [modules/nextflow](https://github.com/nextflow-io/nextflow/tree/master/modules/nextflow)
- "Legacy workflows (v1) use raw GPars types: `DataflowBroadcast` (queue channel) and `DataflowVariable` (value channel)." Typed workflows wrap them as `ChannelImpl` and `ValueImpl`. Source: [adr/20260310-typed-workflows.md](https://github.com/nextflow-io/nextflow/blob/master/adr/20260310-typed-workflows.md)
- Multiple inputs: "When a process is defined with multiple inputs, it waits for a value from each input and launches a new task with the combined values. When one of the inputs is a channel, the process repeats until all values in the channel are consumed. If the channel is empty, the process will not launch any tasks." Value inputs are reused for every task. The docs warn: "Do not supply more than one channel when calling a process with multiple inputs," because it can lead to non-deterministic behavior. Source: [docs/process.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/process.mdx)
- Singleton outputs: when a process gets only dataflow values, plain values or no inputs, it returns dataflow values, not channels. The same process called with `channel.of('hello')` returns a channel. Source: [docs/process.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/process.mdx)
- Process input kinds: `val`, `path`, `env`, `stdin`, `tuple`, `each` (input repeater, which creates the Cartesian product). Output kinds: `val`, `path`, `env`, `stdout`, `eval`, `tuple`, with `emit:` names, `optional` and `topic:`. Script kinds: `script` (including conditional scripts), `template`, `shell` (deprecated), and native execution with `exec:`. Other sections: `stub` and `when`. Source: [docs/process.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/process.mdx)
- 41 process directives are documented, including `accelerator`, `afterScript`, `arch`, `array`, `beforeScript`, `cache`, `clusterOptions`, `conda`, `container`, `containerOptions`, `cpus`, `disk`, `errorStrategy`, `executor`, `ext`, `fair`, `hints`, `label`, `machineType`, `maxErrors`, `maxForks`, `maxRetries`, `maxSubmitAwait`, `memory`, `module`, `publishDir`, `queue`, `resourceLabels`, `resourceLimits`, `scratch`, `secret`, `spack`, `stageInMode`, `stageOutMode`, `storeDir`, `tag` and `time`. Source: [docs/reference/process/directives/](https://github.com/nextflow-io/nextflow/tree/master/docs/reference/process/directives)
- Directives can be dynamic (closures such as `memory { 2.GB * task.attempt }`). The docs describe dynamic task resources, resources based on the previous execution trace, and dynamic retry with backoff. 25.10 added a simpler syntax for dynamic directives. Source: [docs/process.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/process.mdx); [docs/migrations/25-10.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/25-10.mdx)
- Error strategies (enum `ErrorStrategy`): `TERMINATE` (kill pending and running tasks), `FINISH` (wait for pending and running tasks, then stop), `IGNORE`, `RETRY`. Source: [ErrorStrategy.groovy](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/src/main/groovy/nextflow/processor/ErrorStrategy.groovy)
- Task control files in each work directory: `.command.sh`, `.command.run`, `.command.in`, `.command.out`, `.command.err`, `.command.log`, `.exitcode`, `.command.begin`, `.command.stage`, `.command.trace`, `.command.env`. Source: [TaskRun.groovy](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/src/main/groovy/nextflow/processor/TaskRun.groovy)
- The `.command.run` template (220 lines) defines Bash functions `nxf_stage`, `nxf_unstage_outputs`, `nxf_unstage_controls`, `nxf_launch`, `on_exit`, `on_term` and `nxf_main`. `nxf_main` sets traps, runs `beforeScript`, module/conda/spack activation, task env, secrets, stages inputs, launches the script with stdout and stderr teed to files, unstages, runs `afterScript`, and writes the exit status to `.exitcode`. Source: [command-run.txt](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/src/main/resources/nextflow/executor/command-run.txt)
- The task hash (`TaskHasher.compute()`) includes: session UUID, fully qualified process name, source of the `script:`/`exec:` block, container fingerprint, name and value of each input, `eval` output commands, global variables referenced by the script, referenced `bin/` scripts, module bundle fingerprint, `module`, `conda`, `spack` and `arch` directives, and more. Source: [TaskHasher.groovy](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/src/main/groovy/nextflow/processor/TaskHasher.groovy)
- The default hash function is `Hashing.murmur3_128()` (Guava). File hashing modes are `STANDARD`, `DEEP`, `LENIENT` and `SHA256`. Source: [HashBuilder.java](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-commons/src/main/nextflow/util/HashBuilder.java); [CacheHelper.java](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-commons/src/main/nextflow/util/CacheHelper.java)
- The resume cache store uses LevelDB (`DefaultCacheStore`). Source: [DefaultCacheStore.groovy](https://github.com/nextflow-io/nextflow/blob/master/modules/nextflow/src/main/groovy/nextflow/cache/DefaultCacheStore.groovy)
- `storeDir` keeps outputs in a permanent directory. A task is skipped when the declared outputs already exist there. It is deprecated in 26.10 in favor of explicit workflow logic. Source: [store-dir.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/process/directives/store-dir.mdx)

### Inferences
- The dataflow core is small in concept: bounded or unbounded FIFO channels, write-once values, and processes that fire when all inputs are ready. It maps well to Rust async (for example tokio mpsc channels and shared futures). The hard parts are exact firing and ordering rules. Examples: value versus queue inputs, singleton outputs, `each`, the end-of-channel signal (a "poison pill" in GPars) and how it spreads through operators, and "the process runs once when all inputs are values".
- Byte-for-byte compatibility with Nextflow task hashes is not needed and not realistic, because the hash covers Groovy AST source text and Java object hashing. iunctus should define its own cache key and keep the same spirit (script text, inputs, container, relevant directives).
- The `.command.run` wrapper is a practical, well-tested design. iunctus can write its own Bash wrapper with the same responsibilities: staging, stdout/stderr capture, exit-code file, traps. Keeping the same file names helps users who debug with Nextflow habits. The Nextflow code is Apache-2.0 licensed, but reusing it verbatim should be a deliberate license decision.
- `exec:` processes run arbitrary Groovy inside the JVM. A native implementation can support them only if the body stays inside the supported expression subset.

### Gaps
- There is no formal specification of operator and process firing semantics (ordering guarantees, end-of-stream propagation). Only prose docs and code exist.
- The exact `-resume` lookup (work directory probing, `.exitcode` checks, output re-collection) was not traced line by line in `TaskProcessor.groovy`.

## Q4. Channel factories and operators

### Takeaway
There are about 50 legacy operators. Since 26.04 the docs mark them as "Operators (legacy)" and define a much smaller typed core: `collect`, `combine`, `filter`, `flatMap`, `groupBy`, `join`, `map`, `mix`, `reduce`, `subscribe`, `unique`, `until` and `view`. Real nf-core pipelines still use the legacy set heavily. The hard operators are the ones that depend on ordering, block until the end of a channel, or parse file formats.

### Cited Findings
- The legacy operator reference lists: `branch`, `buffer`, `collate`, `collect`, `collectFile`, `combine`, `concat`, `count`, `countFasta`, `countFastq`, `countJson`, `countLines`, `cross`, `distinct`, `dump`, `filter`, `first`, `flatMap`, `flatten`, `groupTuple`, `ifEmpty`, `join`, `last`, `map`, `max`, `merge`, `min`, `mix`, `multiMap`, `randomSample`, `reduce`, `set`, `splitCsv`, `splitFasta`, `splitFastq`, `splitJson`, `splitText`, `subscribe`, `sum`, `take`, `tap`, `toList`, `toSortedList`, `transpose`, `unique`, `until`, `view`. The page is titled "Operators (legacy)" and says "Added in version 26.04: See Operators for the core operator reference." Source: [docs/reference/operator.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/operator.mdx)
- Eight of these operators carry the warning "This operator depends on the ordering of values in the source channel. It can lead to non-deterministic behavior if used improperly." (for example `buffer`, `collate`, `distinct`, `first`, `merge`, `take`). `collectFile` needs local temporary storage. `splitFasta` and `splitFastq` keep chunks in memory unless `file: true` is set. `groupTuple`'s `sort` option is discouraged. Source: [docs/reference/operator.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/operator.mdx)
- The typed `Channel<E>` API lists: `collect() -> Value<Bag<E>>`, `combine`, `filter`, `flatMap`, `groupBy`, `join(other: Channel<Record>, by:, remainder:)`, `map`, `mix`, `reduce`, `subscribe`, `unique`, `until`, `view`. Source: [docs/reference/stdlib-types/channel.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/stdlib-types/channel.mdx)

Source: [docs/reference/stdlib-namespaces/channel.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/stdlib-namespaces/channel.mdx)

### Inferences
- Easy (stateless, per item): `map`, `flatMap`, `filter`, `view`, `set`, `tap`, `dump`, `ifEmpty`, `mix`, `concat`, `flatten`, `transpose`.
- Medium (stateful but local): `unique`, `distinct`, `take`, `until`, `first`, `last`, `buffer`, `collate`, `count`, `sum`, `min`, `max`, `reduce`, `branch`, `multiMap`, `combine` (Cartesian product; must buffer both sides), `cross`, `merge`.
- Hard or subtle: `join` (key matching, `remainder`, `failOnDuplicate`, `failOnMismatch`), `groupTuple` (needs `size` or a `groupKey` to emit early, otherwise waits for end of channel), `collect`, `toList`, `toSortedList` (block until end of channel, return value channels), `collectFile` (sorting, file merging, temp storage), and the `split*`/`count*` family (FASTA, FASTQ, CSV, JSON and text parsing with Groovy-compatible options, gzip handling, record chunking, `file: true` chunk files).
- The typed core (13 operators) is a good first target for the operator engine. The legacy set can then be layered on it. Many legacy operators are compositions of core ones.
- `ordering`: Nextflow does not guarantee order across a process's outputs (tasks finish in any order). Tests should compare multisets, not sequences, unless the pipeline sorts.

### Gaps
- The exact semantics of `groupKey` and `groupTuple(size:)` early emission and `remainder` were not verified in code.
- It was not measured which legacy operators are used across all nf-core pipelines (only rnaseq was measured).

## Q5. The Groovy dependency

### Takeaway
Even strict-syntax Nextflow is Groovy at runtime. Real pipelines use closures, GStrings, the Groovy collections and string API (GDK), regex, `file()` and Path helpers, and in places fully qualified Java and Groovy classes (JSON, YAML, template engines, GZIP). There is no Groovy interpreter written in Rust. Only tree-sitter Groovy parsers exist. A native interpreter must re-implement a well-defined subset of Groovy semantics plus the Nextflow standard library, and it must provide shims for a small set of commonly used Java classes.

### Cited Findings
- Classes imported by default in scripts: `groovy.lang.*`, `groovy.util.*`, `java.io.*`, `java.lang.*`, `java.math.BigDecimal`, `java.math.BigInteger`, `java.net.*`, `java.util.*`. "Any Groovy or Java class that is available to Nextflow at runtime can be used in a Nextflow script." Other classes need fully qualified names. Source: [docs/reference/stdlib-groovy.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/stdlib-groovy.mdx)
- The strict-syntax guide replaces `for` loops with `each`, `collect`, `find`, `findAll` and `inject`, and points to the Groovy standard library (GDK) docs for them. Source: [docs/strict-syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/strict-syntax.mdx)
- "Any Groovy code can be moved into the `lib` directory, which supports the full Groovy language." Plugins are the other way to keep Groovy code. Source: [docs/strict-syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/strict-syntax.mdx)
- The documented typed standard library covers `Bag`, `Boolean`, `Channel`, `Duration`, `Float`, `Integer`, `Iterable`, `List`, `Map`, `MemoryUnit`, `Path` (13 KB of docs), `Record`, `Set`, `String`, `Tuple`, `Value`, `VersionNumber`, plus the namespaces `channel`, `global`, `log`, `nextflow` and `workflow`. Source: [docs/reference/stdlib-types](https://github.com/nextflow-io/nextflow/tree/master/docs/reference/stdlib-types); [docs/reference/stdlib-namespaces](https://github.com/nextflow-io/nextflow/tree/master/docs/reference/stdlib-namespaces)
- Measured in `nf-core/rnaseq` (strict-syntax pipeline, `nextflowVersion = '!>=25.10.4'`, commit of 23 Sep 2026): 108 `.nf` files (10,554 lines), 150 `.config` files (4,621 lines), 58 `def` functions, 24 regex operators (`=~`, `==~`), 5 `template` scripts (`.r`, `.py`, `.pl`). There is no `lib/` directory. Common GDK and Path methods: `.join` 130, `.contains` 59, `.size` 45, `.name` 44, `.endsWith` 35, `.baseName` 29, `.first` 21, `.replace` 13, `.trim`/`.toLowerCase`/`.text`/`.split`/`.extension`/`.each` about 11 each, `.unique`/`.tokenize`/`.flatten` 10 each, then `replaceAll`, `keySet`, `eachWithIndex`, `drop`, `toList`, `sort`, `readLines`, `collectEntries`, `any`, `subMap`. Source: [nf-core/rnaseq](https://github.com/nf-core/rnaseq) (grep counts made for this note)
- Fully qualified JVM classes used in rnaseq `.nf` and `.config` files: `groovy.json.JsonSlurper` (3), `org.yaml.snakeyaml.Yaml` (3), `groovy.json.JsonOutput.prettyPrint`/`toJson`, `java.util.Date`, `java.util.zip.GZIPInputStream`, `java.nio.file.Paths.get`, `java.nio.file.Files.getLastModifiedTime`, `groovy.text.SimpleTemplateEngine`, `groovy.text.GStringTemplateEngine`, `new File(...)` (6). They appear in the shared `utils_nfcore_pipeline` and `utils_nextflow_pipeline` subworkflows and in a few pipeline subworkflows. Source: [nf-core/rnaseq subworkflows](https://github.com/nf-core/rnaseq/tree/master/subworkflows)
- Example config closure from rnaseq `conf/modules/*.config`: `ext.args = { def strandedness = meta.strandedness == 'forward' ? '--fr' : meta.strandedness == 'reverse' ? '--rf' : ''; [ strandedness, '-v' ].join(' ').trim() }`, and `publishDir = [ path: { "${params.outdir}/${task.ext.publish_prefix}${params.aligner}/stringtie" }, mode: params.publish_dir_mode ]`. Source: [nf-core/rnaseq conf/modules](https://github.com/nf-core/rnaseq/tree/master/conf/modules)
- Rust crates for Groovy parsing exist: `tree-sitter-groovy` (from amaanq/tree-sitter-groovy, about 1,800 downloads) and `dekobon-tree-sitter-groovy`. Community grammars also exist (murtaza64, chernetskyi). Source: [crates.io tree-sitter-groovy](https://crates.io/crates/tree-sitter-groovy); [docs.rs dekobon_tree_sitter_groovy](https://docs.rs/dekobon-tree-sitter-groovy/latest/dekobon_tree_sitter_groovy/); [dekobon/tree-sitter-groovy](https://github.com/dekobon/tree-sitter-groovy)
- A crates.io search for "nextflow" (2026-09-27) returned no Nextflow parser or interpreter crate. It returned only bioinformatics tools. Source: [crates.io search API](https://crates.io/api/v1/crates?q=nextflow)

### Inferences
- No Groovy interpreter written in Rust was found. The parsers above give syntax only, with no evaluation.
- The Groovy semantics subset a native interpreter needs (inferred from the grammar, the semantics doc and rnaseq usage):
  - Dynamic values: null, Boolean, Integer/Long/BigInteger, BigDecimal (Groovy decimal literals are BigDecimal by default, and `/` on integers gives a decimal), Double, String and GString, List, Map (insertion-ordered `LinkedHashMap`), Set, Range, closures, Path, Duration (`1.h`), MemoryUnit (`2.GB`), records and tuples.
  - Groovy truthiness, `==` meaning `equals()` with numeric promotion, `<=>`, `in`, the Elvis operator, safe navigation, spread-dot, list and map literals, `+` and `-` on collections and maps, `<<` append, index and negative index, slicing with ranges, `as` casts, `instanceof`.
  - GString interpolation (`$x`, `${expr}`), including lazy closures inside strings. Multi-line strings with `stripIndent` rules for process scripts. Escape handling that must match what Bash then sees.
  - Closures with explicit parameters, implicit `it` (deprecated but still used), destructuring of list arguments into closure parameters (`{ meta, reads -> }` on a tuple), delegate resolution for directives and config blocks, and named arguments collected into a map.
  - About 100 to 150 GDK and JDK methods on String, List, Map, Set, Iterable and Path (the `types/shim` files in nf-lang define the typed subset).
  - Regex with Java semantics (`=~` returns a matcher, `==~` a full match, `~/pattern/` slashy strings). Rust's `regex` crate has no backreferences or lookaround. `fancy-regex` or a Java-compatible engine would be needed.
  - A small set of JVM class shims: JSON (JsonSlurper, JsonOutput), YAML (snakeyaml), `GStringTemplateEngine`/`SimpleTemplateEngine` (also used by process `template` files), GZIP input streams, `java.util.Date`, `java.nio.file.Files`/`Paths`, `File`.
- Pipelines with a `lib/` directory, custom Groovy classes, `exec:` bodies using arbitrary Java APIs, or third-party jars cannot be supported without a JVM. They should be detected and rejected with a clear message.

### Gaps
- It was not measured how many of the 144 tracked nf-core pipelines still have a `lib/` directory, use `exec:` processes, or use fully qualified Java classes. The strict-syntax health report does not show this. Measuring it needs a scripted clone of all pipelines.
- It was not verified how Nextflow's strict parser treats Groovy number semantics (for example whether `1/2` is still `0.5` BigDecimal). The semantics doc section on numbers was not read in full.

## Q6. Configuration (nextflow.config, includeConfig, profiles, selectors)

### Takeaway
Configuration is a second language with its own grammar. It has nested scopes, `includeConfig`, `profiles`, `params`, and process selectors (`withName:`, `withLabel:`) whose values are often closures evaluated per task. nf-core's own Python tooling does not parse config itself. It shells out to `nextflow config -o json`. That shows that config resolution is hard to do statically.

### Cited Findings
- `ConfigParser.g4` defines `configInclude`, `configAssign`, `configBlock`, `configSelector` and `configApplyBlock` on top of the shared expression grammar. Source: [ConfigParser.g4](https://github.com/nextflow-io/nextflow/blob/master/modules/nf-lang/src/main/antlr/ConfigParser.g4)
- The strict config syntax forbids mixing config statements with scripting statements and forbids referencing config settings as variables. Source: [docs/strict-syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/strict-syntax.mdx)
- The strict parser now validates process selectors without the false warnings that the deprecated `nextflow.enable.configProcessNamesValidation` flag addressed. Source: [docs/migrations/25-10.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/25-10.mdx)
- nf-core/rnaseq config usage: a top-level `params { }` block, a `process { }` block, `includeConfig 'conf/base.config'`, about 20 profiles (debug, conda, mamba, docker, singularity, podman, shifter, charliecloud, apptainer, wave, test, test_gpu, test_full, test_prokaryotic and more) that themselves contain `includeConfig` and nested `process` blocks, 457 `withName` selectors, 10 `withLabel` selectors, 195 `ext.args*` settings, 17 uses of `task.attempt`, and `resourceLimits`. Generated per-platform container config files live in `conf/` (for example `containers_docker_amd64.config`, `containers_singularity_oras_arm64.config`). Source: [nf-core/rnaseq nextflow.config](https://github.com/nf-core/rnaseq/blob/master/nextflow.config); [nf-core/rnaseq conf](https://github.com/nf-core/rnaseq/tree/master/conf)
- nf-core/tools `fetch_wf_config` calls `run_cmd("nextflow", f"config -o json {wf_path}")`. Source: [nf-core/tools nf_core/utils.py](https://github.com/nf-core/tools/blob/main/nf_core/utils.py)
- An nf-core blog post reports that a survey found 57 configs in the nf-core/configs repository that were not compliant with the Nextflow syntax at that time. Source: [nf-core blog: Making nf-core/configs strict syntax compliant](https://nf-co.re/blog/2026/configs-strict-syntax) (from a search snippet; the page was not fetched in full)

### Inferences
- Config needs a real evaluator, not a static reader. Values can be closures (`ext.args`, `publishDir.path`, dynamic `memory`) that must be evaluated lazily in the task context (`task`, `meta`, `params`).
- Selector precedence must match Nextflow: generic process settings, then `withLabel`, then `withName`, with regex and negation patterns, and fully qualified names such as `'WORKFLOW:SUBWF:PROC'`. The exact priority rules must be taken from the config docs and tested against real Nextflow.
- Parameter precedence (CLI `--x`, `-params-file`, config `params`, script `params` block defaults) must match. Otherwise nf-core test profiles will not resolve the same inputs.
- The institutional configs in nf-core/configs (loaded remotely through `custom_config_base`) are a separate compatibility surface. The first version can skip them.

### Gaps
- The exact selector priority and merge semantics were not verified in `ConfigBuilder`/`ProcessConfig` source code.
- The exact current number of non-compliant nf-core/configs files was not verified.

## Q7. Plugins

### Takeaway
Plugins are JVM jars loaded at runtime (PF4J based, from the Nextflow plugin registry). A native implementation cannot load them. It must re-implement the few that pipelines depend on. For nf-core, `nf-schema` is effectively required. Cloud file systems (nf-amazon, nf-google, nf-azure) and TES (nf-ga4gh) are features that iunctus would provide natively anyway.

### Cited Findings

Source: [docs/migrations/24-10.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/24-10.mdx)
- 25.10 introduced the Nextflow plugin registry. Source: [docs/migrations/25-10.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/migrations/25-10.mdx)

It validates parameters against the pipeline schema, validates sample sheets (CSV, TSV, JSON, YAML), prints help and summaries, and creates "a type-casted list from a parsed sample sheet". Source: [nf-core/rnaseq nextflow.config](https://github.com/nf-core/rnaseq/blob/master/nextflow.config)

### Inferences
- Native re-implementation priority for iunctus:
  1. `nf-schema` functions: `validateParameters`, `paramsSummaryMap`, `paramsSummaryLog`, `paramsHelp`, `samplesheetToList`. They need a JSON Schema validator (Rust has mature crates, for example `jsonschema`) and nf-schema's custom keywords and type casting rules. This is required for almost every nf-core pipeline.
  2. Object storage paths (`s3://`, `gs://`, `az://`, `https://`) as inputs and outputs, which replace nf-amazon, nf-google and nf-azure. The Rust `object_store` crate covers most of this.
  3. TES execution (the nf-ga4gh role), which is iunctus's own executor layer.
  4. Provenance output (the nf-prov role). iunctus could emit RO-Crate or its own format.
- Plugins that should be ignored or rejected with a warning: `nf-wave` (Seqera container build service), `nf-tower`/`nf-seqera` (Seqera Platform), `nf-slack` and other notification plugins, and `nf-agent`. `include { x } from 'plugin/<name>'` for an unknown plugin should be a clear error.

### Gaps
- nf-schema's custom JSON Schema keywords and casting rules (for example `exists`, `format: file-path`, `meta` fields in sample sheet schemas) were not listed in detail here.
- No usage statistics exist for plugins other than nf-schema across nf-core pipelines.

## Q9. Existing non-JVM work, parsers, translators, and TES support

### Takeaway
No reimplementation of the Nextflow runtime outside the JVM was found. Non-JVM work is limited to parsers for editors and linters (tree-sitter grammars, a small Python parser) and to translators that go into Nextflow, not out of it. TES support exists through the `nf-ga4gh` plugin (v1.5.0, July 2026). Source: [nextflow-io/nf-ga4gh](https://github.com/nextflow-io/nf-ga4gh); [releases](https://github.com/nextflow-io/nf-ga4gh/releases)
- nf-ga4gh README: "While the TES API is designed to abstract workflow managers from direct storage access, Nextflow still needs to access the shared work directory used by your TES endpoint." Config uses `tes.endpoint` (default `http://localhost:8000`, no trailing slash), `timeout`, `pollInterval` (default 5 s), `tags`, and basic, API key or OAuth authentication. It suggests Funnel as a local TES server. Source: [nf-ga4gh README](https://github.com/nextflow-io/nf-ga4gh)
- How the TES task is built (from `TesTaskHandler.groovy`, 429 lines): a process without a container fails ("the container image was not specified"). The TES executor command is `bash -o pipefail -c "bash /work/.command.run 2>&1 | tee /work/.command.log"` with `workdir = /work`. Inputs are `.command.sh`, `.command.run`, remote `bin/` files, `.command.in` (if present) and every staged input file. Outputs are `.command.out`, `.command.err`, `.command.log`, `.exitcode`, plus each declared output file pattern (type `FILE` or `DIRECTORY`), with URLs that point back into the Nextflow work directory. Resources set are CPU cores, RAM and disk. The code has `@TODO preemptible` and `@TODO zones`. Task states treated as complete: `COMPLETE`, `EXECUTOR_ERROR`, `SYSTEM_ERROR`, `CANCELED`. Source: [TesTaskHandler.groovy](https://github.com/nextflow-io/nf-ga4gh/blob/main/src/main/groovy/nextflow/ga4gh/tes/executor/TesTaskHandler.groovy)
- The whole TES executor package is 811 lines of Groovy (handler, executor, bash builder, file copy strategy), plus a generated TES client. Source: [nf-ga4gh tes/executor](https://github.com/nextflow-io/nf-ga4gh/tree/main/src/main/groovy/nextflow/ga4gh/tes/executor)
- A Microsoft Tech Community post (September 2024, older information) presents Nextflow with GA4GH TES on Azure (TES on Azure). Source: [Microsoft Tech Community](https://techcommunity.microsoft.com/blog/healthcareandlifesciencesblog/introducing-nextflow-with-ga4gh-tes-a-new-era-of-scalable-data-processing-on-azu/4253160)

### Inferences
- The nf-ga4gh design is a useful blueprint for iunctus's TES mapping of a Nextflow task: one TES executor per task, the wrapper and script uploaded as inputs, each staged file as a TES input, output globs as TES outputs, and resources from `cpus`, `memory` and `disk`. iunctus can do better on three points: (1) pass input URLs straight from object storage without a shared work directory; (2) map `time`, `accelerator` and preemptible hints to TES `resources`/`backend_parameters` where the server supports them; (3) avoid the `tee` pipe so that exit codes and logs are handled cleanly.
- Nextflow output glob patterns (for example `*.bam`, `**/*.txt`, `{a,b}`) do not map one to one onto TES output wildcard semantics. This needs a clear rule, for example writing a manifest inside the task and uploading whole directories.
- There is no prior art to reuse for a Nextflow runtime outside the JVM. iunctus would be the first. This is both a risk (nothing to copy) and a differentiator.

### Gaps
- The TES specification version that nf-ga4gh targets (1.0 or 1.1) was not confirmed from its generated client.
- No independent report on nf-ga4gh reliability at scale (for example with Funnel or TES on Azure) was found.

## Q10. A realistic first subset, how to verify it, and what a native Rust implementation needs

### Takeaway
A realistic first target is "strict-syntax DSL2 without `lib/`, custom classes or `exec:` JVM code". That means untyped processes with `val`/`path`/`tuple`/`each` inputs, the core plus the common legacy operators, config with profiles, selectors and closures, the `nf-schema` functions, and the local and TES executors. It can be verified against nf-core modules first and then against the lint-clean nf-core pipelines, using their committed nf-test snapshots (stub mode first). Reaching nf-core-level compatibility is a multi-person-year effort with high risk from the Groovy long tail and from Nextflow's fast evolution.

### Cited Findings
- The strict parser is the default since 26.04, and new features need it. Source: [docs/strict-syntax.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/strict-syntax.mdx)
- 100% of nf-core modules (2,087) and subworkflows (123), and 66.7% of pipelines (96 of 144), are lint-clean under Nextflow 26.09.1-edge. Source: [nf-core/strict-syntax-health](https://github.com/nf-core/strict-syntax-health)
- nf-core pipelines ship nf-test snapshots with task counts, output path lists and md5 sums, including stub variants. Source: [nf-core/rnaseq tests](https://github.com/nf-core/rnaseq/tree/master/tests)
- The typed operator core has 13 operators. Source: [docs/reference/stdlib-types/channel.mdx](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/stdlib-types/channel.mdx)
- Size of what is being re-implemented: `nf-lang` about 24,900 lines of Java, the `modules/nextflow` runtime about 97,000 lines of Groovy/Java, grammar 3,165 lines. Counted locally. Source: [nextflow-io/nextflow](https://github.com/nextflow-io/nextflow)

### Inferences

#### Suggested first subset (phase 1)
- Scripts: strict syntax only. `include` (local paths only at first), `params` (legacy `params.x = ...` and the `params { }` block), functions, workflows (`take`/`main`/`emit`, named and entry workflows, `.out` access, pipe `|` and `&`), processes (untyped inputs and outputs: `val`, `path`, `tuple`, `each`, `env`, `stdout`, `eval`, `emit:`, `optional`, `topic:`), `script`, `template`, `stub`, `when`.
- Expressions: the Groovy subset listed in Q5, with the ~100 to 150 most used GDK methods, and Java-compatible regex.
- Operators: the 13 typed core operators plus `branch`, `multiMap`, `groupTuple`, `join` (tuple form), `combine`, `collect`, `flatten`, `first`, `ifEmpty`, `toList`, `set`, `splitCsv`, `concat`, `unique`, `transpose`, `collectFile` (basic). Defer `splitFasta`, `splitFastq`, `buffer`, `collate`, `merge`, `cross`, `randomSample`.
- Config: scopes, `includeConfig`, `profiles`, `params`, `process` with `withName`/`withLabel`, closures, `env`, `docker`/`singularity`/`apptainer` scopes, `resourceLimits`, `executor` basics.
- Plugins: native `nf-schema` functions. Other plugin includes give a clear error.
- Execution: local executor with Docker/Singularity/Apptainer, and TES. Work directory layout, wrapper script, staging by symlink or copy, `publishDir` (modes `copy`, `symlink`, `link`, `move`), `errorStrategy` retry with dynamic resources, `-resume` with an iunctus-specific hash.
- Rejected with a clear message: `lib/` Groovy classes, `exec:` bodies outside the subset, arbitrary `new` on non-shimmed JVM classes, `NXF_SYNTAX_PARSER=v1`-only code, and plugins other than nf-schema.

#### Verification plan
1. Parser conformance: parse all nf-core modules and subworkflows (2,087 plus 123 files) with zero errors. Compare the AST shape with `tree-sitter-nextflow` or with `nextflow lint` results on the same files. Running `nextflow` in CI for comparison is allowed, because it is not used at runtime.
2. Module-level runs: run each nf-core module's nf-test cases (`tests/main.nf.test` with its `.snap`) in stub mode, then in real mode for a sample. Compare output names and md5 sums.
3. Pipeline-level runs: run lint-clean pipelines with `-profile test,docker` and `-stub`. Compare with `tests/*.nf.test.snap` (task count, output path list, md5 of stable files). Then run the real test profile.
4. Differential testing: for a fixed set of pipelines, run real Nextflow and iunctus on the same inputs. Compare the task graph (process names, task count per process, input file sets per task) and the published outputs as multisets.
5. Semantics unit tests: port the documented examples in `docs/snippets/*.nf` with their `.out` files. These are small, executable specifications for operators and language features.

#### What a native Rust Nextflow implementation needs (checklist)
- [ ] Lexer and parser for scripts, following `ScriptParser.g4`/`ScriptLexer.g4`. Newline-sensitive statement ends, slashy and dollar-slashy strings, GString interpolation, triple-quoted strings.
- [ ] Lexer and parser for config, following `ConfigParser.g4`/`ConfigLexer.g4`.
- [ ] Name resolution and include graph (relative paths, then `nf-core/<module>` registry paths, `plugin/<name>` includes, `params` scoping across modules).
- [ ] An expression evaluator with Groovy-compatible dynamic semantics: number tower (Integer, Long, BigInteger, BigDecimal, Double), truthiness, equality and comparison, collections, maps with insertion order, closures with destructuring, GStrings, ranges, safe navigation, Elvis, spread-dot, casts.
- [ ] A standard library: String, List, Map, Set, Iterable, Path (name, baseName, simpleName, extension, text, readLines, exists, size, listFiles/listDirectory, copyTo and more), Duration, MemoryUnit, VersionNumber, the `file()`/`files()` globals, `log`, `workflow` and `nextflow` namespaces, `error()`, `checkIfExists`.
- [ ] JVM class shims: JSON (JsonSlurper, JsonOutput), YAML, GString and simple template engines (also for process `template` files), GZIP streams, `Date`, `File`, `Files`, `Paths`.
- [ ] Java-compatible regex (backreferences, lookaround, `Matcher` groups), probably through `fancy-regex` plus adapters.
- [ ] Config evaluator: scopes, `includeConfig` (local and remote URLs), profiles (ordered), params precedence (CLI, params file, config, script), selectors with Nextflow priority, lazy closures evaluated per task, `env`, container scopes.
- [ ] Dataflow engine: queue and value channels, end-of-stream propagation, process firing rules (value reuse, singleton outputs, `each` products), `maxForks`, topic channels, `.out` and `emit` handling.
- [ ] Operators: typed core (13) plus common legacy ones, with documented ordering behavior. File splitters (CSV first, FASTA and FASTQ later).
- [ ] Task model: directive resolution (static and dynamic), `task.*` properties (attempt, cpus, memory, ext, index, process, hash), `when`, `stub`, script rendering, `template` rendering.
- [ ] Work directories and wrapper: hashed task directories, `.command.sh`, a Bash wrapper (staging, stdout/stderr capture, exit code, traps, `beforeScript`/`afterScript`, container launch), output collection with Nextflow glob rules (including `**`, braces, hidden files, `includeInputs`, `arity`).
- [ ] Caching and resume: a deterministic task hash (script text, inputs, container, relevant directives), file fingerprint modes (path + size + mtime, deep content hash), a persistent cache store (for example SQLite or sled), and reuse of completed work directories.
- [ ] Error handling: `terminate`, `finish`, `ignore`, `retry`, `maxRetries`, `maxErrors`, dynamic resources on retry, exit-code-based closures.
- [ ] Publishing: `publishDir` (path closures, modes, `pattern`, `saveAs`, `enabled`, `overwrite`) and the `output { }` block with index files.
- [ ] Executors: local (with resource accounting), TES (inputs and outputs by URL, resources, polling, auth), and later HPC and cloud batch.
- [ ] Remote paths: `https://`, `s3://`, `gs://`, `az://` for `file()` and channel factories, with local staging or pass-through to TES.
- [ ] Native nf-schema: JSON Schema 2020-12 validation, sample sheet parsing (CSV, TSV, JSON, YAML) with type casting and `meta` fields, help and summary output.
- [ ] Workflow metadata and reports: `workflow.*` properties, `onComplete`/`onError` handlers, trace file (nf-core tests read `workflow.trace`), a version YAML through topic channels.
- [ ] Later: records and typed processes and workflows (`nextflow.enable.types`), `groupBy`, record `join`, the module registry, and `agent` blocks (probably out of scope).

#### Effort and risk estimate (inference, not sourced)
- Parser (script and config) with AST and diagnostics: about 1.5 to 3 person-months. Low to medium risk, because the ANTLR grammar and tree-sitter-nextflow give a precise target.
- Groovy-compatible evaluator and standard library, JVM class shims and regex: about 3 to 5 person-months. High risk. The long tail of GDK behavior (number promotion, string coercion, `toString()` of collections inside GStrings that end up in Bash scripts) causes silent differences in generated commands.
- Config evaluator with selectors, profiles and params precedence: about 1.5 to 2.5 person-months. Medium risk.
- Dataflow engine and operators: about 2.5 to 4 person-months. Medium to high risk (subtle firing and ordering rules, `groupTuple`/`join` edge cases, splitters).
- Task execution, wrapper, staging, globbing, caching, error strategies, publishing: about 3 to 4 person-months. Medium risk.
- Native nf-schema: about 1 person-month. Medium risk (custom keywords and casting).
- TES executor and remote paths: about 1.5 to 2.5 person-months. Medium risk. The TES side is simple, but storage and credentials handling is not.
- Verification harness (module and pipeline snapshots, differential runs): about 1.5 to 2 person-months, and it continues afterwards.
- Total to run a meaningful share of lint-clean nf-core pipelines' test profiles: about 15 to 24 person-months (roughly 1.3 to 2 person-years) for an experienced Rust team. Full parity (legacy v1 syntax, `lib/` Groovy, arbitrary JVM classes, all plugins) is not achievable without a JVM.
- Ongoing cost: Nextflow releases edge versions monthly and stable versions twice a year, with language changes in each. Keeping up likely needs about 0.3 to 0.5 of a full-time engineer permanently. The nf-core move to records and typed processes (mandatory by Q2 2027) forces the typed features onto the roadmap within about a year of a first release.
- Largest risks, in order: (1) Groovy semantic fidelity in string and command generation; (2) the moving language target (types, records, modules, agents); (3) config and selector resolution parity; (4) operator ordering and blocking semantics; (5) nf-core pipelines outside the lint-clean third, and helpers that call JVM classes.

### Gaps
- The effort numbers are estimates by analogy with the measured code sizes. They are not based on any comparable project, because no comparable project was found.
- It was not checked whether `docs/snippets/*.nf` and `*.out` cover enough operators to act as a conformance suite.
- It was not checked whether the Nextflow license (Apache-2.0) and the nf-core licenses (MIT) put any constraint on reusing test snapshots and wrapper templates. Both are permissive licenses, but reuse should still be confirmed.
