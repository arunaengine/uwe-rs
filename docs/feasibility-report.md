# Unify tasks, not languages, to build iunctus

Yes, iunctus is feasible. But the answer differs sharply by language. **CWL is already solved in Rust.** FAIRagro's `commonwl` passes 375 of 378 CWL v1.2 conformance tests on a GA4GH TES backend. St. Jude's Sprocket already runs **WDL** natively and also talks to TES. **Nextflow is feasible only as a subset.** That subset is strict-syntax DSL2 without custom Groovy classes or JVM code. It needs a new Groovy-subset interpreter and costs about 15 to 24 person-months. It would also be the first Nextflow runtime outside the JVM. **Snakemake is feasible for shell rules with light Python.** Full compatibility needs embedded CPython, because 27 of 33 sampled workflows import pandas while the job graph is being built. The design that fits all of this is not one shared workflow graph. Cromwell tried that for WDL and CWL, and it dropped CWL in 2022. iunctus should instead share a value model, a task model and one runtime. Each language keeps its own rules in its own driver. The task graph grows at run time, driven by an append-only event log, and each concrete task maps one to one onto a TES task. The estimates in the research add up to roughly **2.5 to 4 person-years** for CWL, two Snakemake tiers and the Nextflow subset. Nextflow then needs a part-time engineer, permanently, to keep up with its releases. Aruna helps a lot, because it offers S3-compatible storage and a TES interface that pins input versions. Its TES subset is narrow, though: one executor, `s3://` URLs only, no inline content and no directory entries. iunctus should target that narrow task shape from the start.

## Feasibility ranges from already done (CWL) to only partly possible (Snakemake)

The four languages sit at very different points. The table gives the verdict, and the sub-sections explain it. All effort numbers come from the research notes. They are judgement calls for experienced Rust engineers. Only the CWL numbers can be checked against an existing Rust engine. For the other languages, no comparable project exists to calibrate against.

| Language | Verdict | What a native engine can cover | Effort | Risk | Main obstacle |
|---|---|---|---|---|---|
| CWL v1.0 to v1.2 | Feasible, already proven in Rust | About 99% of the v1.2 conformance suite | 3 to 6 person-months with reuse of `commonwl` parts, 8 to 13 from scratch | Medium | Output collection on object storage, and differences between TES servers |
| WDL (later) | Feasible, already proven in Rust | High, through Sprocket's crates | Not estimated in the notes; reuse makes it small | Low to medium | Sprocket is pre-1.0 and changes often |
| Nextflow (strict-syntax DSL2) | Feasible for a subset | Lint-clean nf-core pipelines without `lib/` Groovy, custom classes or unsupported Java classes | 15 to 24 person-months, then 0.3 to 0.5 of a full-time engineer permanently | High | Groovy runtime semantics, and a fast-moving language |
| Snakemake 9.x | Feasible for a subset; full coverage needs CPython | Shell rules with config, `expand`, lambdas and simple helper functions | 4 to 6 (tier 1), plus 6 to 9 (tier 2), plus 6 to 12 (tier 3) | High | Python that runs while the job graph is built |

### CWL: a Rust engine already passes 375 of 378 tests on TES

CWL is the easy case. It is a written specification with a large test suite. The current standard is **v1.2.1**, tagged on 2024-01-03 ([cwl-v1.2 releases](https://github.com/common-workflow-language/cwl-v1.2/releases)). Version 1.3 is still an unreleased draft, and its main new feature is loops. The v1.2 suite has **378 tests, 84 of them marked "required"** ([conformance tests](https://github.com/common-workflow-language/cwl-v1.2/blob/main/conformance_tests.yaml)). 134 tests need JavaScript. None of the required tests do. So a runner without JavaScript can pass every required test, but real-world CWL uses JavaScript often.

The strongest evidence is a working engine. FAIRagro's `commonwl` is about 20,500 lines of Rust under MIT OR Apache-2.0. In its CI run of 2026-09-17 it passed **376 of 378 tests locally, and 375 of 378 on Docker and on TES** (Funnel plus S3-compatible storage) ([commonwl CI run](https://github.com/fairagro/commonwl/actions/runs/35203037834)). Two of the failures come from large numbers, because `serde_json` stores every number as a 64-bit float. It evaluates JavaScript with the pure-Rust Boa engine. So a native CWL runner on TES is not a research question any more. It is an engineering task.

The hard parts are known, and they are not in the workflow graph. They are output collection on object storage (globs, symlinks, Directory outputs, empty directories, `cwl.output.json` and checksums), InitialWorkDir, the type system and command-line binding, and correct id resolution in Schema Salad preprocessing. TES makes some of this harder. It has no writable inputs and no field for network isolation ([TES OpenAPI](https://github.com/ga4gh/task-execution-schemas/blob/develop/openapi/task_execution_service.openapi.yaml)). No Rust code generator for Schema Salad exists. The only attempt is a draft pull request that has stalled ([schema_salad PR #917](https://github.com/common-workflow-language/schema_salad/pull/917)). `commonwl` also has no code to upgrade v1.0 and v1.1 documents on load, which cwltool does. iunctus must add that. The research estimate is **8 to 13 person-months from scratch, or about 3 to 6 with reuse of `commonwl` parts**, at medium risk. The reuse risk is about people, not code. Almost all of the project's 643 commits come from one developer, and the work is grant funded ([fairagro/commonwl](https://github.com/fairagro/commonwl)).

### WDL: Sprocket already runs WDL in Rust and talks to TES

WDL is not in the first scope. It is still the cheapest language to add later. St. Jude's Sprocket (v0.31.0, 2026-09-16, MIT OR Apache-2.0) is a Rust WDL engine with separate crates for grammar, syntax tree, analysis and engine ([Sprocket](https://github.com/stjude-rust-labs/sprocket)). Its engine has local, Docker, Apptainer, Slurm, LSF and TES backends ([wdl-engine backends](https://github.com/stjude-rust-labs/sprocket/tree/main/crates/wdl-engine/src/backend)). It calls those backends through its own `TaskExecutionBackend` trait ([backend.rs](https://github.com/stjude-rust-labs/sprocket/blob/main/crates/wdl-engine/src/backend.rs)). By inference, iunctus can reuse the analysis crate for parsing and type checking, and plug its own executor in behind that trait. The risk is churn. Sprocket is pre-1.0, and its configuration "is expected to undergo significant changes" ([Sprocket project status](https://sprocket.bio/about/project-status)). The WDL specification also moves: v1.3.0 came out on 2026-01-12 ([openwdl/wdl](https://github.com/openwdl/wdl)). The notes contain no effort estimate for WDL, so a short spike should size it.

### Nextflow: a formal grammar makes a subset possible, but the runtime is still Groovy

Two recent changes make a native Nextflow engine possible at all. First, Nextflow now has a formal grammar. It is written in ANTLR 4, is 3,165 lines long, and has about 180 parser rules for scripts and config ([nf-lang grammar](https://github.com/nextflow-io/nextflow/tree/master/modules/nf-lang/src/main/antlr)). Second, the strict parser that uses this grammar has been **the default since Nextflow 26.04**. Since 25.10, all new language features need it, and the legacy parser is announced for removal ([strict syntax docs](https://github.com/nextflow-io/nextflow/blob/master/docs/strict-syntax.mdx)). Strict syntax removes `import`, class declarations, `for` and `while` loops, and `switch`. That turns "all of Groovy" into a bounded language.

The grammar only defines syntax, though. The meaning still comes from Groovy. The Nextflow team says so directly: its strict-parser design lists "Replacing the Groovy runtime" as a non-goal ([strict parser ADR](https://github.com/nextflow-io/nextflow/blob/master/adr/20250508-strict-syntax-parser.md)). Real pipelines use closures, GStrings, about 100 to 150 methods from Groovy's standard library extensions (the GDK), Java-style regular expressions and some Java classes. nf-core/rnaseq, for example, uses `JsonSlurper`, SnakeYAML, Groovy template engines and `GZIPInputStream` in its shared helper subworkflows ([rnaseq subworkflows](https://github.com/nf-core/rnaseq/tree/master/subworkflows)). No Groovy interpreter exists in Rust. The only candidate crate is two months old and has 109 downloads ([groovy crate](https://crates.io/crates/groovy)). Compiling Groovy with GraalVM native image is no shortcut either, because dynamic Groovy is "almost 99% incompatible" with it ([klokwrk article](https://github.com/croz-ltd/klokwrk-project/blob/master/support/documentation/article/groovy-graalvm-native-image/groovy-graalvm-native-image.md)). So iunctus must write a Groovy-subset interpreter from scratch. The worst risk here is silent drift. A small difference in number formatting or string conversion changes the Bash command a task runs, and nothing fails.

Configuration is a second language. nf-core/rnaseq alone has 457 `withName` selectors, about 20 profiles, and closures that run once per task ([rnaseq nextflow.config](https://github.com/nf-core/rnaseq/blob/master/nextflow.config)). nf-core's own Python tools do not even try to parse it. They shell out to `nextflow config -o json` ([nf-core/tools utils.py](https://github.com/nf-core/tools/blob/main/nf_core/utils.py)). Plugins are JVM jars, so iunctus cannot load them. Almost every nf-core pipeline needs `nf-schema`, so its functions must be rewritten natively ([nf-schema](https://github.com/nextflow-io/nf-schema)). The runtime being replaced is large: about 97,000 lines of Groovy and Java on top of the GPars dataflow library ([modules/nextflow](https://github.com/nextflow-io/nextflow/tree/master/modules/nextflow)). The dataflow core itself maps well onto Rust async channels. The hard parts are the exact firing and ordering rules, and about 50 legacy operators. The newer typed core has only 13 operators, which makes a good first target ([typed channel API](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/stdlib-types/channel.mdx)).

Nobody has done this before. The research found no Nextflow runtime outside the JVM, in any language ([crates.io search](https://crates.io/api/v1/crates?q=nextflow)). The target also moves fast. Stable releases come every April and October, and edge releases every month ([release policy](https://github.com/nextflow-io/nextflow/blob/master/docs/updating-nextflow.mdx)). nf-core will make static types and records mandatory by **Q2 2027** ([nf-core roadmap](https://nf-co.re/blog/2025/nextflow_syntax_nf-core_roadmap)). The estimate is **15 to 24 person-months** to run a meaningful share of lint-clean nf-core pipelines, plus 0.3 to 0.5 of a full-time engineer permanently. Good test data keeps this manageable. **All 2,087 nf-core modules and 96 of 144 tracked pipelines (66.7%) pass `nextflow lint` today** ([strict-syntax-health](https://github.com/nf-core/strict-syntax-health)). Pipelines also ship nf-test snapshots with task counts and md5 sums, including stub-mode variants that skip the real tools ([rnaseq tests](https://github.com/nf-core/rnaseq/tree/master/tests)).

### Snakemake: Python sets the ceiling for any native engine

Snakemake is the opposite of Nextflow. Its rule syntax is easy to parse, but its meaning is not. Snakemake has no formal grammar. Its `parser.py` rewrites a Snakefile into Python, and Snakemake then runs that Python ([parser.py](https://github.com/snakemake/snakemake/blob/main/src/snakemake/parser.py)). Rules are registered as a side effect of running top-level code. The author of OxyMake, a Rust engine with a Snakemake translator, puts it plainly: "the full job graph is known only after the workflow file is executed" ([OxyMake paper](https://arxiv.org/abs/2606.20989)).

Real workflows use a lot of Python. For this study the researchers scanned 33 real repositories with 1,753 rules. **31 define helper functions, 27 use lambdas, and 27 import pandas** ([snakemake-workflows organisation](https://github.com/snakemake-workflows)). This Python splits into two kinds. Job-time Python (`script:`, `wrapper:`, `run:`) can run inside the job's container, like any other tool. Python that runs while the job graph is built (config handling, input functions, sample sheets) must run inside iunctus. That second kind decides how native iunctus can be.

The research compared four interpreters for it. Monty 1.0.0 from pydantic, released on 2026-09-25, is a Rust sandbox with a fixed standard library and no third-party imports ([Monty](https://github.com/pydantic/monty)). RustPython 0.5 is "not totally production-ready" and cannot load C extensions such as pandas ([RustPython](https://github.com/RustPython/RustPython)). Starlark is not Python, so every workflow would need rewriting. Only CPython, embedded through PyO3, runs pandas-based Snakefiles. It needs a Python install with the right packages on the host ([PyO3 guide](https://pyo3.rs/v0.29.2/building-and-distribution.html)).

The execution side is simpler, and it fills a real gap. The existing Snakemake TES plugin (v0.1.3, last release 2024-03-12) does not send the real tool command to TES. It runs Snakemake again inside every task. An issue asking for a "native" TES executor, with real commands, real images and real TES inputs and outputs, has been open since 2023 ([plugin issue #3](https://github.com/snakemake/snakemake-executor-plugin-tes/issues/3)). A 2026 issue reports that the plugin sends an empty `outputs` list, so jobs fail with missing files ([plugin issue #19](https://github.com/snakemake/snakemake-executor-plugin-tes/issues/19)). iunctus would be the native executor that issue #3 asks for.

The notes define three tiers. Tier 1 is shell rules with static values (4 to 6 person-months, medium risk). Tier 2 adds an embedded interpreter, input functions, modules and checkpoints (6 to 9 more, high risk). Tier 3 adds scripts, wrappers, conda and storage (6 to 12 more). Full parity without CPython is not realistic. The language also keeps moving: 9.x had 27 minor releases in about 18 months, and a breaking `software:` directive is already on `main` ([Snakemake changelog](https://github.com/snakemake/snakemake/blob/main/CHANGELOG.md); [PR #3339](https://github.com/snakemake/snakemake/pull/3339)). Snakemake's own test folder gives a ready first milestone. Of 395 test folders with expected results, **139 need no Python helpers, scripts, checkpoints or software environments** ([Snakemake tests](https://github.com/snakemake/snakemake/tree/main/tests)).

## Earlier projects stalled at embedded code or dropped a language

Many converters between workflow languages exist. None handles real Nextflow or Snakemake pipelines completely. CNT, an academic CWL-to-Nextflow translator, reached **73% and 81% automatic coverage** on two pipelines. It replaced JavaScript with placeholders that break the build on purpose ([CNT paper](https://ucare.cs.uchicago.edu/pdf/bibe23-cnt.pdf)). Janis warns that output often needs manual fixes because of "freeform Javascript (CWL), Java / Groovy (Nextflow), and Python / Cheetah (Galaxy)" ([Janis docs](https://janis.readthedocs.io/en/translate-docs/index.html)). wf2wf, a converter built around one intermediate representation (IR), is the closest match to the iunctus idea. It parses Nextflow with regular expressions and runs the `snakemake` binary to get the job graph ([wf2wf](https://github.com/csmcal/wf2wf)). Its IR is a static task graph, and it has had no commits since 2025-07-15.

Platforms that run several languages mostly wrap the original engines. Latch runs the real Nextflow as a subprocess ([Latch Nextflow](https://wiki.latch.bio/workflows/sdk/nextflow/overview)). Sapporo runs each engine in its own container ([Sapporo](https://github.com/sapporo-wes/sapporo-service)). Toil hosts CWL and WDL, but through two separate translators of 5,442 and 6,283 lines, built on cwltool and miniwdl ([cwltoil.py](https://github.com/DataBiosphere/toil/blob/master/src/toil/cwl/cwltoil.py); [wdltoil.py](https://github.com/DataBiosphere/toil/blob/master/src/toil/wdl/wdltoil.py)). The best-known shared IR was Cromwell's WOM, which hosted WDL and CWL. **Cromwell 79 was the last release with CWL** ([Cromwell changelog](https://github.com/broadinstitute/cromwell/blob/develop/CHANGELOG.md)). Broad explained that it would be "more productive" to focus on WDL and run other languages on tools the community already uses ([Terra blog](https://terra.bio/terras-roadmap-to-supporting-more-workflow-languages/)). The code shows the cost. WOM's shared task type grew fields that exist for one language's rules only ([CommandTaskDefinition.scala](https://github.com/broadinstitute/cromwell/blob/develop/wom/src/main/scala/wom/callable/CommandTaskDefinition.scala)).

The workflow community reached the same conclusion in 2021: "Systems that use the same underlying abstractions can likely be translated between, which is not the case for systems that use different abstractions" ([Workflows Community Summit](https://arxiv.org/abs/2106.05177)). Nextflow pushes data through channels. Snakemake pulls jobs backwards from target files. CWL is a static step graph. Sharing did work where it happened at the task level. The remote execution API used by Bazel is shared by at least seven build tools and six servers ([remote-apis](https://github.com/bazelbuild/remote-apis)). TES itself is a task-level standard.

The lesson for iunctus is to execute, not translate. A translator needs an equivalent target construct for every source construct. An engine only needs to run the construct. That removes most of the failure history. The part that stays hard is the part that broke the translators: evaluating embedded Groovy, Python and JavaScript with their original meaning. Two more lessons come from the survivors. Silent partial support made past converters untrustworthy, so the better tools fail loudly. wf2wf has `--fail-on-loss`, and OxyMake refuses checkpoints and modules unless the user passes `--lossy` ([OxyMake parser](https://github.com/noogram/oxymake/blob/main/crates/ox-translate/src/snakemake/parser.rs)). And one-person converters go stale within one to two years, while tools backed by a platform or a standards group survive.

## Share values, tasks and one runtime, not one workflow graph

The IR should have two layers. The workflow layer keeps each language's own rules. The task layer is shared by all languages and maps onto TES. An event loop connects the two and lets the task graph grow while the run is in progress.

### The workflow layer keeps each language's own rules

Each language gets its own program model behind a common driver interface. The shared runtime only sees that interface, the values and the task records. The drivers still share a small vocabulary, so that validation, planning and visualisation can be shared. A callable is a task template with typed input and output ports. Its command template is opaque and language specific. Its resource expressions can read the inputs and the attempt number. Nodes can be calls, expressions, maps (scatter), conditionals, gathers, sub-workflows, stream operators and planners. Expressions stay opaque, as in WOM's expression interface: declared inputs, evaluate a value, evaluate a type, list files, and give a cache string ([WomExpression.scala](https://github.com/broadinstitute/cromwell/blob/develop/wom/src/main/scala/wom/expression/WomExpression.scala)). Edges come in two kinds. CWL and WDL use single-value edges. Nextflow uses stream edges, which are its channels.

Values use one model for all languages. They are JSON-like typed values plus File and Directory references. A file reference holds a location URI, a content digest when known, the size, the basename and optional secondary files. Numbers must stay exact, because `commonwl` loses two CWL tests to 64-bit floats. The three languages then map very differently onto this vocabulary. For CWL and WDL, the whole graph is known at load time, so iunctus can type-check it and show a plan before anything runs. For Nextflow, only the network of processes, operators and channels is known at load time. Tasks appear at run time. For Snakemake, a planner node holds the rules and the targets. The job graph is known after backward planning, up to the first checkpoint.

### The task layer maps one to one onto a TES task

Every concrete task is a fully resolved record in three parts. Only the first part goes into the cache key.

| Part of the task record | Contents | In the cache key? |
|---|---|---|
| Hashed specification: what is computed | Container image (resolved to a digest where possible); executor steps (argv, working directory, environment, stdin, stdout and stderr paths); inputs (container path, file or directory, content digest, size, source URI or inline content); outputs (path or glob, file or directory, required or optional, the port it feeds); driver name and version | Yes |
| Placement: where and how big | CPU cores, RAM, disk, preemptible, zones, backend parameters (GPUs, time limits, queues), output destination URLs, tags, chosen backend | No |
| Attempt record: what happened | Stable task identity, cache key, attempt number, TES task id, state, logs, exit codes, output digests and sizes, timings | No |

The cache key is a digest of the hashed specification, much like the action digest in the remote execution API. That API also has a `salt` field, which puts actions into a separate cache namespace so that poisoned results can be dropped ([remote_execution.proto](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto)). Resources stay out of the key, as they do in Sprocket's call cache ([Sprocket cache.rs](https://github.com/stjude-rust-labs/sprocket/blob/main/crates/wdl-engine/src/cache.rs)). So a retry with more memory keeps the same key. Files are hashed by content. A cheap check by path, size and modification time can be an optional fast path. The session id stays out of the key, so the cache works across runs. This differs from Nextflow, whose resume is tied to one session and to an existing work directory ([Nextflow cache and resume](https://docs.seqera.io/nextflow/cache-and-resume)). Byte-for-byte compatibility with Nextflow's task hashes is not realistic, because they cover Groovy source text and Java object hashing.

CWL shows why a plain "command plus files" record is not enough. A CWL command line depends on runtime values such as cores and the output directory. Its outputs are defined by evaluation after the run: globs, `outputEval` and `cwl.output.json`. So the driver needs hooks before and after each task. It builds the command before the task and collects outputs from storage after it. Between the two layers, planning passes do the work that Pegasus showed ([Pegasus mapping](https://pegasus.isi.edu/documentation/reference-guide/mapping.html)). They look up the cache, place and stage data, bundle very short tasks into one TES task, and clean up intermediate files that no pending task needs.

### An event loop and an append-only log handle graphs that grow at run time

Each driver implements two operations. "Start" returns the first task requests. "On event" takes a completion event (outputs as values, or a failure) and returns new task requests or "done". This follows miniwdl, whose state machine "evaluates WDL expressions locally, while instructing the driver when to call tasks/subworkflows" ([miniwdl](https://github.com/chanzuckerberg/miniwdl/blob/main/WDL/runtime/_workflow_state.py)). A Nextflow driver keeps input queues per process and runs operators in-process. Each task's identity comes from a hash of its content, so arrival order does not change it. This matters because some operators, such as `mix`, give items "in any order" ([Nextflow operators](https://github.com/nextflow-io/nextflow/blob/master/docs/reference/operator.mdx)). A Snakemake driver plans backwards from the targets. Jobs that depend on a checkpoint wait. When a checkpoint job finishes, the driver plans again and keeps the unchanged jobs, matched by rule plus wildcard values.

Every decision goes into an append-only log. That covers submitted tasks, finished tasks with output digests, scatter lengths, checkpoint results and any other non-deterministic choice. On resume, iunctus replays the log to rebuild driver state and reuses finished tasks through their cache keys. This is how Temporal resumes: a recorded side effect "does not re-execute upon replay, but instead returns the recorded result" ([Temporal events](https://docs.temporal.io/workflow-execution/event)). Temporal also shows the scale limit. It warns after 10,240 events and terminates an execution above 51,200. So iunctus needs one log per sub-workflow, or periodic snapshots, from the start. Retries go through the driver. It re-evaluates resource expressions with the next attempt number and emits a new attempt with the same cache key. Three rules keep the design honest. Do not build one static graph as the only IR. Do not add language-specific fields to the shared task record. And do not rely on TES for retries, caching, output digests or time limits.

## Send conservative TES tasks and keep intermediate data in S3

TES is a small and stable target. The latest release is **v1.1, tagged on 2022-11-15**, and no later version has shipped ([TES releases](https://github.com/ga4gh/task-execution-schemas/releases)). A TES task is one containerized batch job with inputs, executors that run one after another, outputs, resources and logs. It has no dependencies, no retries, no GPU field and no wall-time field. `cpu_cores` is an integer, so fractional CWL cores must be rounded up. Inline input `content` is only guaranteed up to 128 KiB ([TES OpenAPI](https://github.com/ga4gh/task-execution-schemas/blob/develop/openapi/task_execution_service.openapi.yaml)).

Servers differ in practice. The GA4GH compatibility matrix from August 2026 marks Funnel as compatible with most clients, Planetary as not compatible with Snakemake, and Poiesis as not compatible with Sprocket ([TES README](https://github.com/ga4gh/task-execution-schemas/blob/develop/README.md)). Microsoft's TES on Azure was retired on 2025-08-04 ([microsoft/ga4gh-tes](https://github.com/microsoft/ga4gh-tes)). Funnel (v0.11.14, 2026-06-11) is the best server for local tests and CI ([Funnel releases](https://github.com/calypr/funnel/releases)). Existing TES clients keep hitting the same problems. Nextflow's TES plugin still needs a shared work directory that both Nextflow and the TES server can reach ([nf-ga4gh](https://github.com/nextflow-io/nf-ga4gh)). A request for an object-store path has been open since 2022 ([nf-ga4gh #2](https://github.com/nextflow-io/nf-ga4gh/issues/2)). The same plugin reads the first task log, although servers that retry append a newer one ([nf-ga4gh #6](https://github.com/nextflow-io/nf-ga4gh/issues/6)). Crankshaft hard-codes `ignore_error` to true, which Poiesis rejects ([crankshaft #81](https://github.com/stjude-rust-labs/crankshaft/issues/81)).

### Designing for Aruna's narrow TES route makes tasks portable

Aruna v3 is in public testing. Every node offers an S3-compatible interface, and datasets are described with RO-Crate ([Aruna](https://github.com/arunaengine/aruna)). Its TES route is strict. It accepts **exactly one executor**. Input and output URLs must be `s3://bucket/key`. A task may have at most 512 inputs and 1,024 outputs. Directory entries, inline input content, volumes, executor stdin, stdout and stderr redirection, and zones are all unsupported ([Aruna TES route](https://github.com/arunaengine/aruna/blob/main/api/src/routes/execution/tes.rs)). Aruna also has strengths that no other server in the notes offers. It reads every input at the object version that was current when it accepted the task. It reports outputs with exact version ids. It deduplicates submissions through an idempotency-key tag. And it separates permanent tool failures (`EXECUTOR_ERROR`) from infrastructure failures that it re-plans itself (`SYSTEM_ERROR`). Version pinning plus version ids gives iunctus reproducible cache hits and exact provenance.

If iunctus designs for Aruna, the same task works on Funnel, Planetary and Poiesis. So the default task should look like this. Each iunctus task becomes one TES task with one executor. iunctus renders the tool command into a wrapper script. The wrapper changes to a fixed work directory, sets the environment, redirects stdout and stderr to files, runs the command, and writes an exit-code file and an output manifest. The wrapper is uploaded as an `s3://` object, because Aruna rejects inline content. iunctus sets every input's type explicitly, never sends `ignore_error`, and declares every output plus the log, exit-code and manifest files. Resources are rounded up. GPUs and time limits go into `backend_parameters`, but only with keys that the server lists in its service-info. Tags carry the run, task, attempt and cache key, plus Aruna's idempotency key. iunctus polls with one tag-filtered ListTasks call per interval, as Crankshaft does ([Crankshaft TES monitor](https://github.com/stjude-rust-labs/crankshaft/blob/main/crankshaft-engine/src/service/runner/backend/tes/monitor.rs)), and it always reads the last task log.

Three things in this shape need testing before any design is final. First, both CWL engines on TES upload the whole output directory as one DIRECTORY output ([cwl-tes](https://github.com/ohsu-comp-bio/cwl-tes/blob/master/cwl_tes/tes.py); [commonwl TES backend](https://github.com/fairagro/commonwl/blob/main/crates/engine/backend/tes.rs)). If "directory entries" in Aruna's list means DIRECTORY inputs and outputs, which is the natural reading, that approach fails on Aruna. The fallbacks are wildcard outputs with `path_prefix`, which Aruna accepts, or packing the output directory into an archive plus a manifest. Second, ideas that need a second executor must move into the wrapper. That includes `commonwl`'s marker step for empty directories and bundling Snakemake groups into one task. Third, Aruna only accepts `s3://` URLs. So `https://` test data, as used by nf-core test profiles, must be copied into S3 by iunctus first.

Intermediate data should live in an S3-compatible store by default: Aruna, MinIO or a cloud provider. Sprocket shows a layout that works. Local inputs are uploaded once under their content digest. Outputs go to a unique prefix per task execution. Files are downloaded only when the engine must read them ([Sprocket TES backend](https://sprocket.bio/reference/backends/tes)). In iunctus that happens for CWL `loadContents` and `outputEval`, Nextflow operators that read file contents, and Snakemake checkpoints. Everything else stays a URL. An output of one task becomes an input URL of the next without passing through the engine. A shared file system mode remains useful for local and HPC executors.

### Nine operations make up the executor trait

The executor interface should be iunctus's own trait. Aruna's `ExecutorBackend` trait is the richest model in the notes ([Aruna executor trait](https://github.com/arunaengine/aruna/blob/main/compute/src/executor/mod.rs)). Snakemake's explicit capability flags ([Snakemake executor settings](https://github.com/snakemake/snakemake-interface-executor-plugins/blob/main/snakemake_interface_executor_plugins/settings.py)) and Crankshaft's batched polling complete it. The operation names below come from the research notes and are placeholders for discussion.

| Operation | What it does | Precedent |
|---|---|---|
| Capabilities | Reports what the backend supports: several commands per task, inline content, volumes, output globs, directories, GPUs, preemption, URL schemes, input and output limits, shared file system | Snakemake capability flags |
| Prepare | Turns engine inputs into backend locations: upload by digest, or pass remote URLs through | Sprocket TES staging |
| Submit | Idempotent under a deterministic name built from run, task and attempt | Aruna `submit` and idempotency tag |
| Poll | Batched status for many tasks at once (TES ListTasks by tag, Slurm `squeue`) | Crankshaft TES monitor |
| Cancel | Asynchronous; the caller waits for a terminal state | TES cancel endpoint |
| Result | Exit code, times, output files with sizes, resource usage if reported | TES task log |
| Logs | A bounded tail of stdout and stderr, plus a link to the full log files | Aruna `fetch_logs` |
| Reconcile | After an engine restart, finds existing tasks by run tag or name, without changing them | Aruna `reconcile` |
| Cleanup | Removes scratch data after results are durably recorded | Aruna `cleanup` |

Errors fall into four kinds: tool failure, retryable infrastructure failure, preemption and cancellation. They match the TES states. The resource model stays close to TES (CPU, memory, disk, preemptible) plus a free map of backend parameters. With this trait, TES comes first, but local, Docker, Slurm, LSF, Apptainer and Kubernetes can follow. Funnel already reaches Slurm, PBS, Grid Engine, HTCondor, Kubernetes, AWS Batch and Google Batch behind TES ([Funnel compute backends](https://github.com/calypr/funnel/tree/develop/compute)). So a native backend is only needed where TES overhead or its feature gaps hurt.

## Mature crates and test suites make a native engine possible now

Five things make iunctus possible in 2026 when it was not a few years ago. The first is Nextflow's strict syntax, which gives the language a formal grammar and removes the worst parts of Groovy. The second is a set of good test oracles. CWL has 378 conformance tests and the `cwltest` runner ([cwltest](https://github.com/common-workflow-language/cwltest)). Snakemake has about 395 test folders with expected outputs, under an MIT-style license ([Snakemake license](https://github.com/snakemake/snakemake/blob/main/LICENSE.md)). nf-core pipelines ship md5 snapshots. The real engines can also run in CI for differential tests, which does not break the "no engines at run time" rule. The third is embeddable evaluators. Boa 0.22 reaches **95.60% of the ECMAScript test suite** ([Boa v0.22](https://github.com/boa-dev/boa/releases/tag/v0.22)), far beyond the ECMAScript 5.1 that CWL needs. Monty gives a sandboxed Python subset in pure Rust. The fourth is a stable TES 1.1 standard with a mature Rust client. The fifth is two working Rust engines, `commonwl` and Sprocket, that show the full path from parsing to TES.

Below the language layer, everything is covered by mature, active crates. The language layer is where the new work is. There is no Groovy runtime in Rust, no Snakemake engine in Rust, no Rust config grammar for Nextflow, and no pure-Rust Python that can load pandas. The table lists what to reuse. "Depend" means use it as a dependency. "Study" means read it and port ideas.

| Need | Reuse | How | Caveat |
|---|---|---|---|
| CWL parsing and Schema Salad subset | `cwl_core`, `cwl_salad` from [commonwl](https://github.com/fairagro/commonwl) | Depend, or fork | One main maintainer; 15 minor releases in under a year |
| CWL engine logic (output collection, InitialWorkDir, TES mapping) | `cwl_engine` from commonwl | Study and port selected parts | It owns scheduling and staging through crankshaft |
| CWL JavaScript | [`boa_engine`](https://crates.io/crates/boa_engine) 0.22, with `rquickjs` as fallback | Depend, behind a small engine trait | Node-specific behaviour in real `expressionLib` code |

| Parser infrastructure | [`logos`](https://crates.io/crates/logos) and [`rowan`](https://crates.io/crates/rowan) | Depend, following Sprocket's [`wdl-grammar`](https://github.com/stjude-rust-labs/sprocket/tree/main/crates/wdl-grammar) | none |

## A phased plan: roughly 2.5 to 4 person-years, CWL first

The plan starts with CWL for three reasons. It is the cheapest language. It has the best test suite. And it forces the shared core (values, task record, event log, cache, TES backend, S3 staging) to be right before the hard languages arrive. Snakemake tier 1 comes next, because it is cheap and tests a very different driver, the backward planner, early. Nextflow is the largest block. Its parser and Groovy-subset evaluator do not depend on the runtime, so that work can start in parallel with phases 1 and 2 if a second engineer is available.

| Phase | Scope | Effort | Risk | Done when |
|---|---|---|---|---|
| 0. Prepare | Corpus measurements, TES and Aruna probes, talks about reuse, design notes, the decisions below | About 1 to 2 person-months (estimate for this report) | Low | Decisions are written down; the TES test matrix passes or its gaps are known |
| 1. Shared core and CWL | Value model, task record, event log, cache, executor trait, local and TES backends, S3 staging, CWL driver on `cwl_core`, v1.0 and v1.1 upgrade, provenance capture | About 4 to 8 person-months (the CWL reuse estimate plus shared runtime work) | Medium | `cwltest` passes 95% or more locally and on Funnel plus MinIO; the same runs work on an Aruna node |
| 2. Snakemake tier 1 | Rule parser, static evaluator, backward planner, shell command rendering, native TES tasks | 4 to 6 person-months | Medium | The 139 static test folders pass; job sets match real Snakemake dry runs in CI |
| 3. Nextflow subset | Script and config parsers (typed syntax included), Groovy-subset evaluator, dataflow engine, core and common operators, native nf-schema, task wrapper, resume | 15 to 24 person-months | High | All nf-core modules parse; module and pipeline stub snapshots match; test profiles of a chosen set of lint-clean pipelines match |
| 4. Snakemake tier 2 | Embedded interpreter, input functions, modules, checkpoints, groups | 6 to 9 person-months | High | The 191-folder subset (which allows helper functions and lambdas) passes, then the checkpoint and module test folders; selected catalog workflows run on TES |
| 5. Extensions | Snakemake tier 3 (6 to 12 months), WDL through Sprocket's crates, Workflow Run RO-Crate export, optional CPython mode, a WES front end | Varies | Medium | Driven by user demand |

Phases 0 to 4 add up to about 30 to 49 person-months, or roughly 2.5 to 4 person-years. Each per-language estimate includes some TES and storage work that the shared core does only once, so the real total is somewhat lower. With two or three engineers working in parallel, that is about one to two years of calendar time. This is simple arithmetic on estimates that were never calibrated, so treat it as an order of magnitude.

The risks are uneven across phases. The largest single risk is Groovy fidelity in phase 3, because errors there change commands silently. Differential tests against real Nextflow in CI are the main defence. The second is timing. nf-core makes records and typed processes mandatory by Q2 2027, before phase 3 can finish. So the Nextflow parser must handle typed syntax from day one, and typed execution must be planned inside phase 3. The 15 to 24 month estimate does not include it. The third is the Python ceiling in phases 2 and 4. If the phase 0 scan shows that Monty covers few real Snakefiles, the CPython decision below becomes urgent. The fourth is ongoing cost. Three moving languages need owners and CI against every upstream release. Cromwell shows that even a funded team can drop a language when it cannot keep up.

## Seven decisions to make, and the work to do before coding

These decisions shape the architecture. Each one is cheaper to make now than later.

| Decision | Options | Recommendation |
|---|---|---|
| 1. What "native" means | (a) pure Rust only; (b) no workflow engine binary or package at run time, but embedded interpreters are allowed; (c) anything short of shelling out | (b). Also allow the real engines in CI, for differential tests only. |
| 2. CPython through PyO3 for Snakemake | Forbid it; offer it as an optional build feature plus a runtime flag; make it the default | Optional and off by default, with Monty as the default. Never import the `snakemake` Python package. |
| 3. Reuse of `commonwl` | Reference only; depend on `cwl_core`; depend on `cwl_engine` | Depend on, or fork, `cwl_core` and `cwl_salad`. Port engine logic selectively. Talk to FAIRagro first. |
| 4. Reuse of crankshaft | Use it as the executor layer; build an own trait and TES backend on the `tes` crate; mix both | Own trait and own TES backend. Revisit crankshaft later for Docker and HPC. |
| 5. Scope rules | Wide scope with best effort; narrow scope that fails loudly | Nextflow strict syntax only. CWL v1.0 to v1.2 with upgrade on load. Snakemake by tiers. Every unsupported feature fails with a clear error. |
| 6. Cache and resume | Compatible with Nextflow and Snakemake state; iunctus's own | Own content-addressed cache that works across runs. Document the difference for users. |
| 7. Aruna's role | Storage only; storage plus TES target; extend Aruna's TES route | S3 default data plane and first-class TES target. Decide with the Aruna team which TES gaps to close. |

Decision 1 is the most important, because it settles decision 2. PyO3 embeds CPython inside the iunctus process. It never calls the `snakemake` program, so it fits reading (b). But it brings a Python runtime and the workflow's packages onto every host, and environment management becomes iunctus's problem. The strongest argument for allowing it is the data: 27 of 33 sampled workflows import pandas. The strongest argument against it is that a pure-Rust default is what makes iunctus different. An optional mode, off by default, keeps both. A related question is job-time Python. Snakemake's Python script preamble pickles a `Snakemake` object and needs the `snakemake` module inside the container ([script/__init__.py](https://github.com/snakemake/snakemake/blob/main/src/snakemake/script/__init__.py)). 432 of 473 Python wrappers import `snakemake.shell` ([snakemake-wrappers](https://github.com/snakemake/snakemake-wrappers)). A small pure-Python module that iunctus writes and stages as a TES input is not an engine, so it fits reading (b). Wrappers that also import `snakemake_wrapper_utils` (135 of 473) need that package in the container too.

Decisions 3 and 4 are about the same risk: small teams. `commonwl`'s parser is valuable, and its license allows reuse. Its engine, though, owns scheduling and staging, which would duplicate iunctus's core. Crankshaft is a good executor library and powers two engines. Its trait is a single `run` call that returns a future ([crankshaft backend.rs](https://github.com/stjude-rust-labs/crankshaft/blob/main/crankshaft-engine/src/service/runner/backend.rs)). It has no reconcile after an engine restart and no capabilities query. Aruna's narrow TES subset also needs exact control over every field. A TES backend is small anyway. The Nextflow TES executor is 811 lines of Groovy plus a generated client ([nf-ga4gh executor](https://github.com/nextflow-io/nf-ga4gh/tree/main/src/main/groovy/nextflow/ga4gh/tes/executor)), and `commonwl`'s is 350 lines of Rust. Building on the `tes` crate directly costs little and removes a dependency on a pre-1.0 API. Decision 7 is special, because the project owner works on Aruna. Adding DIRECTORY outputs, or inline content for small scripts, to Aruna's TES route would remove the biggest CWL-on-TES workaround at the source.

Several pieces of work should happen before any engine code is written. First, write down the definitions. They cover what "native" means, the scope rules, and how unsupported features fail (CWL's exit code 33 is a model). Also pick a license for iunctus that is compatible with MIT and Apache-2.0 reuse. Second, run the measurements that the research could not do. Scan the 465 standardized Snakemake catalog workflows ([catalog data](https://github.com/snakemake/snakemake-workflow-catalog/blob/main/data.json)) with a real parser, count their Python use, and run Monty on real helper functions. Scan all 144 tracked nf-core pipelines for `lib/` directories, `exec:` blocks, Java classes and plugins, and list which of the 96 lint-clean pipelines have stub snapshots. Check how well `tree-sitter-nextflow` parses full pipelines, not just modules. Third, build a TES test matrix: Funnel with MinIO, an Aruna v3 node, and Planetary on a local Kubernetes cluster. Submit the default task shape to each. Test DIRECTORY inputs and outputs, wildcard outputs with `path_prefix`, empty directories, symlinks, input and output limits, last-log behaviour, and the per-task overhead. Also run the GA4GH [TES compliance suite](https://github.com/elixir-cloud-aai/tes-compliance-suite) against each server. Fourth, talk to FAIRagro about `commonwl` and to St. Jude about `tes`, crankshaft and Sprocket, covering API stability and upstream work. Fifth, write short design notes for the value model, the task record, the driver interface, the event log and the executor trait. Check them on paper against one small workflow per language: an nf-core module, a Snakemake test folder, and a CWL conformance workflow with scatter and InitialWorkDir. Finally, set up the test harnesses before the engines. That means `cwltest` in CI and a manifest of Snakemake test cases extracted from its `tests.py`. It also means a runner that compares nf-core nf-test snapshots, and differential runs against the real engines in CI.

## Conclusion

The project's name (Latin for "joined") states the right idea, as long as the joining happens at the right level. iunctus should join languages at the level of the concrete task and the runtime, not at the level of a shared workflow language. In the research, every system that joined independently designed tools or languages successfully did it there: the remote execution API, Nix derivations, and TES itself. Every attempt to force different languages into one workflow graph or one translation either stalled at embedded code or dropped a language. Nextflow and Snakemake also have inverse profiles, and this should drive the plan. Nextflow has a high native ceiling but a high entry cost. Strict syntax bounds the Groovy it needs, yet a whole interpreter must exist before the first pipeline runs. Snakemake has a low entry cost but a low native ceiling. Its rules parse easily, but pandas blocks most curated workflows unless CPython is allowed. So the definition of "native" is not a philosophical question. It decides how many real Snakemake workflows iunctus can ever run.

Aruna turns out to be more than a storage backend. Its narrow TES route forces a task shape that runs on every other TES server as well. Its version pinning gives iunctus reproducible caching and exact provenance almost for free. And because the owner works on Aruna, the biggest CWL-on-TES pain, directory outputs, can be fixed where it starts. The main uncertainties are not technical. They are the missing corpus measurements, the untested behaviour of real TES servers, and whether a small team can track three fast-moving languages for years. Phase 0 exists to turn the first two into numbers before any engine code is written. The third needs an explicit staffing commitment.
